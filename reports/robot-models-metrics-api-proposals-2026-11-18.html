Live and offline

How live and offline work, honestly

  • Offline: arm.values(arm.fold(run)) is one pass over the whole recording.
  • Live: state = arm.empty(), then state = arm.update(state, chunk) per chunk, then arm.values(arm.close(state)). On CAN 11's play 32, fed 7 rows at a time, it gives live == offline -> True, equal bit for bit on all 15 numbers. The frozen check holds it to 1e-9.
  • Stops survive chunk boundaries: yes. The stop tracker carries the open dwell across chunks as part of the state. Every stop lasts at least 0.25 s (25+ rows), so 7-row chunks cut through every one of them, and the stops still match the offline ones.
  • Memory is not bounded. Measured after streaming play 32 (318 rows) in 7-row chunks: the lag metric (TimeOffset, a cross-correlation, live=False) holds both whole streams (636 samples) until close. The stop metric keeps each stop's move rows for settle and overshoot (607 samples). The error statistics hold 4 numbers each. So the state grows with the run, about 4x the run's rows here.
  • Time alignment: 0.1.0 has an explicit align / Aligner step with a tolerance, and its own reader uses it (the hermite rule). In this column the fixture already puts the target at each reply's instant, so no metric aligns anything. TimeOffset reads the plan on its own ticks.

Decisions taken inside the direction:

  • Every metric is one number or one bool, as in Keras. The tip stop's median and worst are two StopError objects (statistic="median", statistic="worst"), not one object with two outputs.
  • Units live on the configured object (unit="mm", scale=339.0), never in the class or the math (the stop finder and the sums are SI). One class serves several names: TrackingError for RMS and peak, StopError for median, worst and p90.
  • MetricDict is a real dict (so list(metrics), metrics["tip stop worst (mm)"] and .items() work) with update / compute / reset added. It is torchmetrics' MetricCollection, named for what it is.
  • The one keyword beyond Keras: update(..., new_run=True) starts the next recording inside the same metric. A chunk that goes back in time without it raises, so two recordings are never glued together silently (shown in the session). The glance never needs it.
  • Lag reads the plan as sent (update(run.plan, run.measured), or MetricDict.update(..., plan=run.plan)), not the target at each reply, because that is the oracle's definition.

Prior art

  • keras.metrics: update_state(y_true, y_pred) / result() / reset_state(), one number per metric, the constructor holds the config (MeanSquaredError(name=...)). Taken: the verbs, one number per object, constructor config, name. Not taken: Keras puts thresholds inside some metrics (Precision(thresholds=0.5)); here a threshold never enters a metric.
  • torchmetrics: update(preds, target) / compute() / reset(); MetricCollection with compute groups (members with the same state are updated once); wrappers for per-sample statistics. Taken: the verbs, the collection as a dict, compute groups (the five stop metrics in a dict share one StopFinder, so 7 metrics cost 3 computations per chunk). Not taken: tensors, add_state / merge_state, nn.Module.
  • torchmetrics itself is not imported. Round 1 measured it: 3.9 s and 450 MB at import, 2.7 GB of venv. numpy + robot_msgs does the work here; the core imports numpy, robot_msgs and the stdlib only (matplotlib and Rerun load only inside round 1's _viz sinks).

Live and offline

Live and offline, honestly

  • Offline is one update(run.target, run.measured) on the whole recording. Live is the same object fed chunks (run.target[start:start + 7]); compute() works at any time, mid-run included.
  • Exactly equal, not just close. live == offline is True on CAN 11's play 32 for every metric. The RMS is a running sum in row order, so 7-row chunks and the whole recording add the same numbers in the same order; the stop rule is round 1's per-sample stock.StopTracker, so a stop that straddles a chunk boundary is found the same way.
  • Mid-run, the stop in progress counts as if the run ended now (compute() closes a copy of the tracker; the state never changes). That is what makes the last compute() of a live run equal the offline value.
  • Memory. Tracking keeps running sums: constant. Stop metrics keep one small record per stop (error, settle time per band asked for, overshoot) plus the rows of the move in progress; the move rows are dropped as each stop closes. A median needs every stop, so this grows with the stop count, never with the row count. Lag keeps every row it is given (a cross-correlation needs the run), and Repeatability keeps each repeat's stop errors; both say so.
  • Time alignment is stated, not done. update refuses a target and measured that are not sampled at the same times ("align them first"); round 1's fixture puts the target at each reply's instant, the scorecard's own rule. A chunk that goes back in time without new_run=True is refused.
  • Many runs: one fresh MetricDict per rung cell (rung_table), fed each of the cell's plays with new_run=True. Each metric combines runs by its own stated rule (across_runs, on every card): tracking RMS is the median of the plays' RMS, a peak the worst row of any play, every stop metric pools all the plays' stops (the rung's median stop is the median of all 14 stops, never a median of medians).

Where it would live, and the three copies

  • metrics.py → robot_metrics (this face replacing 0.1.0's empty / update / merge / close vocabulary); the stop rule → robot_msgs.compare.stops, beside goal and estimate_time_offset.
  • part_metrics.py → robot_models, each function beside its family (IntegratedServo.metrics next to its 14 models); PART_TYPES here shows the pairing.
  • The three copies: robot_msgs.compare stays the formula home (goal, overshoot, lag, pose error, and the stop rule once it lands there). sim2real.metrics and robotdx.diagnostics.stock call it instead of their own stop and RMS code, and lose those copies. One copy stays: TrackingError keeps its own running sum of squares, because robot_msgs.compare.error_stats takes a whole array and cannot be fed chunks. That is two RMS implementations, said out loud.

Metric objects with the three verbs every ML engineer already knows: metrics.update(target, measured) as rows arrive, metrics.compute() for the numbers, metrics.reset() to start over. A part's metrics are a dict of those objects keyed by name and unit; the gate is a separate Threshold that reads the computed numbers from outside.

Decisions taken inside the direction:

  • Every metric is one number or one bool, as in Keras. The tip stop's median and worst are two StopError objects (statistic="median", statistic="worst"), not one object with two outputs.
  • Units live on the configured object (unit="mm", scale=339.0), never in the class or the math (the stop finder and the sums are SI). One class serves several names: TrackingError for RMS and peak, StopError for median, worst and p90.
  • MetricDict is a real dict (so list(metrics), metrics["tip stop worst (mm)"] and .items() work) with update / compute / reset added. It is torchmetrics' MetricCollection, named for what it is.
  • The one keyword beyond Keras: update(..., new_run=True) starts the next recording inside the same metric. A chunk that goes back in time without it raises, so two recordings are never glued together silently (shown in the session). The glance never needs it.
  • Lag reads the plan as sent (update(run.plan, run.measured), or MetricDict.update(..., plan=run.plan)), not the target at each reply, because that is the oracle's definition.

Prior art

  • keras.metrics: update_state(y_true, y_pred) / result() / reset_state(), one number per metric, the constructor holds the config (MeanSquaredError(name=...)). Taken: the verbs, one number per object, constructor config, name. Not taken: Keras puts thresholds inside some metrics (Precision(thresholds=0.5)); here a threshold never enters a metric.
  • torchmetrics: update(preds, target) / compute() / reset(); MetricCollection with compute groups (members with the same state are updated once); wrappers for per-sample statistics. Taken: the verbs, the collection as a dict, compute groups (the five stop metrics in a dict share one StopFinder, so 7 metrics cost 3 computations per chunk). Not taken: tensors, add_state / merge_state, nn.Module.
  • torchmetrics itself is not imported. Round 1 measured it: 3.9 s and 450 MB at import, 2.7 GB of venv. numpy + robot_msgs does the work here; the core imports numpy, robot_msgs and the stdlib only (matplotlib and Rerun load only inside round 1's _viz sinks).

Live and offline, honestly

  • Offline is one update(run.target, run.measured) on the whole recording. Live is the same object fed chunks (run.target[start:start + 7]); compute() works at any time, mid-run included.
  • Exactly equal, not just close. live == offline is True on CAN 11's play 32 for every metric. The RMS is a running sum in row order, so 7-row chunks and the whole recording add the same numbers in the same order; the stop rule is round 1's per-sample stock.StopTracker, so a stop that straddles a chunk boundary is found the same way.
  • Mid-run, the stop in progress counts as if the run ended now (compute() closes a copy of the tracker; the state never changes). That is what makes the last compute() of a live run equal the offline value.
  • Memory. Tracking keeps running sums: constant. Stop metrics keep one small record per stop (error, settle time per band asked for, overshoot) plus the rows of the move in progress; the move rows are dropped as each stop closes. A median needs every stop, so this grows with the stop count, never with the row count. Lag keeps every row it is given (a cross-correlation needs the run), and Repeatability keeps each repeat's stop errors; both say so.
  • Time alignment is stated, not done. update refuses a target and measured that are not sampled at the same times ("align them first"); round 1's fixture puts the target at each reply's instant, the scorecard's own rule. A chunk that goes back in time without new_run=True is refused.
  • Many runs: one fresh MetricDict per rung cell (rung_table), fed each of the cell's plays with new_run=True. Each metric combines runs by its own stated rule (across_runs, on every card): tracking RMS is the median of the plays' RMS, a peak the worst row of any play, every stop metric pools all the plays' stops (the rung's median stop is the median of all 14 stops, never a median of medians).

Where it would live, and the three copies

  • metrics.py → robot_metrics (this face replacing 0.1.0's empty / update / merge / close vocabulary); the stop rule → robot_msgs.compare.stops, beside goal and estimate_time_offset.
  • part_metrics.py → robot_models, each function beside its family (IntegratedServo.metrics next to its 14 models); PART_TYPES here shows the pairing.
  • The three copies: robot_msgs.compare stays the formula home (goal, overshoot, lag, pose error, and the stop rule once it lands there). sim2real.metrics and robotdx.diagnostics.stock call it instead of their own stop and RMS code, and lose those copies. One copy stays: TrackingError keeps its own running sum of squares, because robot_msgs.compare.error_stats takes a whole array and cannot be fed chunks. That is two RMS implementations, said out loud.

What I'd change

  • Run boundaries are the seam Keras does not have. new_run=True is plain, but it is one more thing to know. A recording type that knows its own start (a Run passed whole) would remove it for offline use; live would still need it.
  • One object per number makes the dict long (7 entries for the arm) and repeats scale= on every tip metric. A small tip(...) helper in part_metrics would shorten it; I kept every constructor visible instead.
  • MetricDict sharing has a sharp edge: once metrics share a stop finder, update the dict, not one member. torchmetrics has the same rule for compute groups; a member could refuse a direct update.
  • Bounded stop memory is possible only by giving up the exact median (a streaming quantile sketch), which fails parity. I would keep it exact.

# a new metric is one plain function (stock.moving: the rows with a commanded speed)
import math
import statistics

import numpy as np
import stock
from run_metrics import as_list

def velocity_error_rms_deg_s(runs):
    """RMS of measured - target speed while the arm moves, in deg/s"""
    per_run = []
    for one_run in as_list(runs):
        moving = stock.moving(one_run.target)
        measured = one_run.measured.velocities[moving, 0]
        target = one_run.target.velocities[moving, 0]
        per_run.append(math.degrees(math.sqrt(np.mean((measured - target) ** 2))))
    return statistics.median(per_run)

How offline and live work, honestly

  • One record per run. Every pendulum metric reads RunTotals: six running sums plus three numbers per finished stop (signed error, settle time, overshoot). Offline, totals_of(run) fills it with the whole run as one chunk and remembers it, so the nine live-capable metrics read run 32's rows once (passes_over_rows(run) gives 1). Live, LiveScore.add(chunk) fills the same record chunk by chunk, and result() calls the same functions on it.
  • Live equals offline bit for bit, not just within 1e-9. The sum of squares is added one row at a time, in arrival order, so chunking can't regroup the additions. The session shows it for chunks of 7 rows and of 1 row: (True, True) on ==.
  • Stops survive chunk boundaries. The stop rule is round 1's per-sample StopTracker. A hold that straddles a chunk boundary is still open when the next chunk arrives, and result() mid-run closes a copy of it, so the record keeps going.
  • Memory is not constant. It holds the six sums, three numbers per stop, and the rows of the move in progress: the stop rule needs the move into a stop for its overshoot and the hold's rows for its settle time. On run 32 that is 175 of its 318 rows at the end (live.kept_in_memory()). So memory stays bounded by the longest move plus its hold, not by the run. A run that never holds still would keep every row.
  • Time alignment is required, not done here. add() checks that the target and measured rows share their instants, and raises if they don't. The fixture already samples the plan at each reply's own instant. Raw topics that arrive apart would need an aligner first (robot_metrics 0.1.0's Aligner, or robot_msgs.compare's align).
  • Whole-run metrics say so. lag_ms (estimate_time_offset searches the whole recording), faulted_runs (the outcome is known at the end) and the five-bar's ErrorStats rows are live=False. LiveScore([lag_ms]) raises "lag_ms needs the whole run" instead of quietly buffering the run.

Direction

The direction and its prior art

  • Polars expressions (group_by().agg()): a column expression (pl.col("x").median()) is evaluated per group. Here the "column" is a measure of each recording (its stops, its moving rows) and the expression is its summary. Polars' own verbs are kept: group_by, agg, filter(**constraints), with_columns, select, pivot, join, vstack, transpose, explode, explain.
  • pandas named aggregation (df.groupby(...).agg(worst=("stop", "max"))): agg(worst_mm=tip_stop_error.max()) names a column; without a name the expression names itself ("worst tip stop (mm)").
  • dplyr summarise (group_by(station, rung) |> summarise(worst = max(stop))): the same shape in R, and the reason "summarise" is the word the page uses.
  • Polars LazyFrame.explain(): Runs.explain(...) prints which computations run over each recording and which metrics read each one (5 computations serve the arm's 11 metrics).

Live and offline

Offline and live, honestly

  • One code path. Each shared computation is a reader with add(chunk) and finish(); each summary a running total with add(values) and value(). Offline adds the whole recording once; live adds 7 rows at a time. On CAN 11 play 32 every live-capable metric of the arm equals offline (equals(..., within=1e-9) is True; the parity check's Z2 row passes to 1e-9).
  • Memory between chunks (Live.memory() prints it):
    • the stop finder holds the rows since the last stop: one move and one dwell, never the run;
    • an RMS or a share holds 2 numbers, a worst value, a count or a flag holds 1;
    • a median (or any percentile) keeps every value it has seen, because an exact median needs them all. For a median tip stop that is one float per stop (2 on play 32, 84 for all of CAN 11): it grows with the stops, not with the rows. A bounded sketch (P², t-digest) would not reproduce the scorecard's exact medians.
  • Stops are safe across chunk boundaries. A dwell still open at a boundary stays open inside the stop finder until a later chunk closes it. result() counts an open stop as if it ended now, on a copy, so the feed goes on.
  • Time alignment is stated, not done here. The fixture puts the target at each reply's own instant (the scorecard's align: measured), and Live assumes target and measured arrive on the same rows. A raw-topic aligner (round 1's v3 Aligner) would sit in front of Live.
  • Lag is offline only. estimate_time_offset is a cross-correlation over the whole recording; Live refuses it by name instead of buffering the run silently.

Pooled vs per run is stated per metric, in the column name and in the card: stops are pooled over a cell's runs ("median tip stop (mm)": the median of every stop in the cell); tracking is per run, then the median across runs ("tracking RMS, median over runs (deg)", written tracking_error.rms().per_run().median()). The glance's tracking_error.rms() is the pooled RMS over every moving row, the plain Polars meaning, so its numbers differ from the scorecard's per-run median (CAN 11 rung 0.9: 0.140 deg pooled, 0.135 deg as the median run).

One formula in one place (fr6)

No per-recording number here has its own formula: the error is robot_msgs.compare's, overshoot is robot_msgs.compare.goal, lag is robot_msgs.compare.estimate_time_offset, and the stop rule is round 1's shared stock.StopTracker. README: r2-4 · Checklist with targets

Direction

A part's metrics are a short checklist. Every row reads as a sentence: its name, how it is measured, the unit it is shown in, its target and who set the target. card.check(run) prints pass / fail per row with the measured value; card.check(runs, by=["station", "rung"]) says, per row, how many groups pass and names the ones that fail. A row with no target is measured and shown as "observed".

Check("worst tip stop", measure=worst_stop_error(at="tip"), unit="mm", target="<= 1.0", owner="Zach 2026-11-11")

Zach's rule, kept literally: "separate the calculation of the metric, and the checking of thresholds". measure= computes one number in SI with no threshold anywhere inside it; the row carries the unit, the target and the owner; the card does the comparing. A wrong unit fails when the row is built (mm on an angle raises).

Prior art

  • Great Expectations, expect_column_values_to_be_between(column, min_value, max_value, mostly=...): an expectation suite is a list of expectations; its metrics compute an observed_value, the expectation only judges it, and validation returns one result per expectation. Here: a card is the suite, a Check the expectation, measure= the metric, and report.results lists one record per (group, row) the same way. GE's mostly is why the median and the worst stop are two rows: "worst tip stop <= 1.0" is mostly=1.0 on every stop; "median tip stop <= 1.0" is mostly=0.5.
  • pytest-benchmark: one table row per benchmark with its statistics side by side, and --benchmark-compare-fail=mean:5% thresholds that live outside the measurement. Here: card.measure(..., by=...) prints one row per group with each check's number in its unit.
  • OpenSLO objectives (displayName, op, value): a target is an operator and a number beside the indicator, never inside it. Here: target="<= 1.0", and the owner rides beside it (OpenSLO carries ownership as metadata).

Live and offline

How live and offline work (honestly)

  • Offline is one update with the whole recording; live is live.update(chunk) per chunk, through the same robot_metrics states. card.check(live) checks the chunks so far.
  • Equal: on CAN 11's play 32 (the glance's recording), 7-row chunks give bit-identical numbers to offline (card.measure(live) == card.measure(run) is True). One-row chunks give the same stops and the same stop errors; the sums differ by 2.8e-17 (float round-off in a sum taken in another order). The parity check's G4 holds at 1e-9.
  • Stops survive chunk boundaries: robot_metrics' stop kernel carries the open dwell across chunks as a value, so a stop split by a chunk edge is found whole. The session shows it with one-row chunks, where every boundary falls inside a move or a stop.
  • Memory is bounded for the sums, not for everything. live.kept() prints what is held: tracking RMS and peak keep 4 numbers, the limiter share 2; the stop rows keep every stop found so far (each with its move's rows, so overshoot can be read at the end) plus the rows of the move still open (175 rows at the end of play 32). lag keeps every row of the run, because a cross-correlation needs the whole run; it is the one end-of-run row and says so.
  • Time alignment is the fixture's: the target is the plan at each reply's own instant. robot_metrics refuses a pair that is not on one clock (check_aligned), so an unaligned live feed fails loudly rather than scoring wrong.
  • Many runs: a pooled row (stops, limiter share) pools every stop or row of the group; tracking RMS is the median of the runs' RMS, the peak the worst run; each measure states its rule (Check.card()["across runs"]). Tip numbers pool within one station only (six stations, six levers): grouping runs of two tip lengths raises.
