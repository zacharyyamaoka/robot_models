Where it lives and what it reads

  • Layering: robot_msgs <- robot_metrics <- robotparts (RobotPart.metrics), with sim2real and RobotDx consuming. robot_models never imports it (Zach: "as we are in robot models all there really is is models").
  • Run data: RunRecording = a stable id, a named map of robot_msgs trajectories (target, state, plan, tool/target, tool/state), labels, an .rrd pointer. This is the run-data MOC's recommendation (the run folder is the contract; streams are a named map; the alias names which pair it compares).
  • Input types: each class declares Input: ErrorStat / DwellError a tracked pair, Repeatability a Repeat (one real repeat of one command, refused otherwise), PerformanceGain a HeldOutPair.

How it works

  • Streaming state: sufficient statistics (sum of squares, count, running max) plus the shared StopTracker, which carries the open dwell across chunk boundaries. Only statistics that cannot reduce keep a "cat" list (medians, the lag's cross-correlation), and each says so in its memory attribute. One live update of the arm's 12 aliases costs 1.4 ms per 7-row chunk.
  • Computed once: an alias's identity is (signal, base class, frozen config). Dwell metrics with one dwell rule on one signal share one Dwells state (torchmetrics' compute groups): the arm's 12 aliases cost 5 computations.
  • Gates: Diagnostic(alias, Limits, owner) and Gate(name, diagnostics) judge the values outside compute(), with RobotDx's rule (strictly beyond a bound trips; no value is not_run, never green).
  • Across runs: a rung is its plays' collections merged with merge_state (pooled stops are exact); PerRun(metric, "median") gives the scorecard's median of per-play RMS.
  • Views: Metric.plot() returns (fig, ax); the same View becomes a W&B table payload and Rerun calls.

What happens to the existing code

  • robotdx.diagnostics.stock: its compute half becomes robot_metrics classes (the config dataclass fields become constructor arguments, scale / unit / limits leave the config for the alias and the Diagnostic). RobotDx keeps Limits, judge, Result and records, and judges robot_metrics values.
  • sim2real.metrics.actuator: deleted; its callers import robot_metrics.functional. Its stop rule and the pendulum's are one DwellRule(include_last_dwell=...).
  • pendulum_score / traj_compare: pendulum_score's per-play numbers are this collection; traj_compare keeps drawing and reads the chain's aliases.
  • CalibrationOutcome lives in robot_metrics.records.

Cost of adding

  • A metric: usually one Alias over a stock base (the session adds velocity-error RMS in one line). New math is a Metric subclass with setup (states), _update, compute.
  • A part type: one PartType(name, models, signals, metrics).

Best when / loses when

Best when you want torchmetrics' muscle memory exactly, and live monitors that run for hours (bounded state). Loses when the state hides in attributes: merging needs every state's reduce rule right, compute() mid-run has to deep-copy the open tracker, and merge_state refuses collections with different configs (stations with different tip lengths merge only through their gates, not their states).

v2 · Family metrics: IntegratedServo.metrics, beside its models

Thesis. The metrics are declared on the part type's ModelFamily, beside its models: IntegratedServo.metrics is a Metrics collection in the family body. A metric's state is a cat buffer and its math one functional twin over (config, runs) (RobotDx's own signature), so the class can never disagree with its function, and one object fed a rung's runs computes the rung by the across_runs= rule in its constructor.

Where it lives and what it reads

  • Layering: robot_msgs <- robot_models (models AND metrics, per type) <- robotparts (a RobotPart reads both from its family) <- sim2real / RobotDx. A type with no ModelFamily yet (rigid_body_chain) is keyed by its type id. In the prototype the metrics are attached to the real IntegratedServo at import; in production they are a class attribute in integrated_servo_family.py.
  • Run data: Episode (the MDP's word): id, named robot_msgs streams, labels, an .rrd pointer.
  • Input types: ErrorStat, Dwell a tracked pair; Repeatability a Repeat; PerformanceGain a HeldOutPair.

How it works

  • Streaming state: update() appends the chunk; compute() concatenates and runs the functional. Exact by construction, a stop across chunks is simply in the buffer. The price: memory O(rows) and 18 ms per compute() on one pendulum play (an append costs 0.01 ms).
  • Computed once: a memo keyed by (identity, which data: run, rows, chunk count) serves every consumer. The servo's 6 aliases, then the arm's 12 on the same recording: 5 new computations, 7 memo hits, 1 stop pass. Dwell is one class with a quantity config (error, settle, overshoot, settled, count) instead of five subclasses.
  • Gates: a Deployment record holds named verdicts of Gate(alias, target), the target a robot_msgs Value with its range and source (who chose it), the noun sim2real's gate() already uses.
  • Across runs: the constructor's across_runs (median, max, pool); Dwell quantities pool.
  • Views: view(collection, alias) builds the stop or run points in the alias's display unit for the shared adapter.

What happens to the existing code

  • robotdx.diagnostics.stock: its functions move into robot_models.metrics with their (config, runs) signature unchanged, so the 89-entry catalog ports by renaming; RobotDx keeps Limits / Result / records.
  • sim2real.metrics.actuator: a re-export of robot_models.metrics until its callers move.
  • CalibrationOutcome lives in robot_models.metrics (beside the fit that produces it).

Cost of adding

  • A metric: one Alias (or a Dwell(quantity=...) config); new math is a subclass with one functional.
  • A part type: a metrics = Metrics(...) line in its family body.

Best when / loses when

Best when offline datasets are the main use and a type's models and metrics should be read in one place. Loses when it runs live for long (the buffer grows and compute re-reads it), and it puts metrics into the models package, against Zach's "all there really is is models" naming ruling and his later "a robot_metrics package".

Where it lives and what it reads

  • Layering: robot_msgs (+ .metrics) <- robotparts' catalog (aliases, Checks, owners: RobotDx's catalog.py moves here) <- sim2real / RobotDx.
  • Run data: Recording = topics (MCAP-like), each a robot_msgs trajectory; messages() replays them in arrival order. A signal names its two topics and its alignment rule (hermite for the rack, same_clock for the five-bar and the sealed ladder).
  • Input types: RootMeanSquare, StopStatistic an AlignedPair; CrossCorrelationLag the raw topics; Repeatability a Repeat; PerformanceGain a HeldOutPair.

How it works

  • Streaming state: the aligner holds at most one reply (a 1-tick latency, stated); metrics keep sufficient statistics, the Stops node the open dwell. One message pair (a knot and a reply) costs 0.66 ms.
  • Computed once: Plan.compile deduplicates by (signal, identity); every StopStatistic reads one shared Stops node. The arm: 12 aliases, 11 nodes, 5 computations including 1 stop pass.
  • Gates: Check(alias, Limits, owner) rows in the catalog, judged on the point estimates.
  • Across runs: each alias says how runs combine (median, max, or pooled:<statistic> over stops and rows); aggregate() adds a seeded bootstrap interval and the IQM, rliable-style.

What happens to the existing code

  • robotdx.diagnostics.stock: its math moves down into robot_msgs.metrics; its catalog.py becomes robotparts' alias catalog. sim2real.metrics.actuator: deleted, callers use robot_msgs.metrics.
  • CalibrationOutcome is a robot_msgs message (robot_msgs.calibration).

Best when / loses when

Best when live streams arrive on their own clocks and alignment must be explicit, and the math should sit at the lowest layer. Loses when robot_msgs grows a metrics framework it was not meant to hold (the prior-art note keeps the math in compare and the classes in robot_metrics), and when an interval is read as a gate: the IQM trims CAN 11's failing stops (the note's §1), so the gates here read point values, not the intervals.

Where it lives and what it reads

  • Layering: a robot_metrics package on robot_msgs, published from io-diagnostics beside RobotDx (the metric half of robotdx.diagnostics lifted out, its parity tests in the same CI); robotparts lists aliases as .metrics.
  • Run data: Run, the run-data MOC's recommendation in full: id, named streams, labels, provenance (real / sim / replay, carried though no metric reads it), outcome, links (rrd through the 8771 launcher, wandb).
  • Input types: ErrorStat, Dwell an aligned pair (checked: same instants within align_tolerance_s); TimeOffset the plan and the state (it finds the offset, so it cannot demand alignment); Repeatability a Repeat; PerformanceGain a HeldOutPair.

How it works

  • Streaming state: tuples and frozen records; the open dwell's tracker is copied into each new state. Each metric declares live (lag: false, needs the run) and a version stored with its values. One live update of the arm's 12 aliases costs 0.97 ms. Stream(metric) is the torchmetrics face (update / compute / reset).
  • Computed once: the collection keys states by (signal, metric) (a frozen metric is its own key) and dwell metrics by (signal, rule): the arm's 12 aliases are 5 states.
  • Gates: Objective(alias, op, value, share, on="items" | "value", owner). The same alias "tip stop error" carries the scorecard's median gate (on its value) and Zach's 1 mm on every stop (on its items). Verdicts are RobotDx's Result (verdict, code, view hint), loaded from io-diagnostics' core.py, not copied.
  • Across runs: summarize(collection, runs, by=("station", "rung")): per stratum the merged states and the runs' own values; a tail per stratum for gates; Wilson intervals for bool metrics (CAN 11: 38 of 42 runs settled every stop, 95 % 0.78-0.96).

What happens to the existing code

  • robotdx.diagnostics.stock: its formulas become these classes, with one fix the note names: limits leave every config, so a new target never changes a metric's identity. RobotDx keeps Limits, judge, Result, records.
  • sim2real.metrics.actuator: deleted, callers use robot_metrics. CalibrationOutcome: a robot_msgs message.

Best when / loses when

Best when states must be stored, resumed, merged across machines or rounds, and gates must state tails honestly. Loses when a new base costs four methods (empty, update, merge, compute), more ceremony than v1's add_state, and when the open tracker is large (each update copies it).

Where it lives and what it reads

  • Layering: robot_msgs <- robotparts (RobotPart: .models from robot_models, .metrics here, .children) <- sim2real / RobotDx. The deployment's tree is its robot description's.
  • Run data: named robot_msgs streams per run, routed to each node by its signals; a node's ledger keeps each run's labels and event logs.
  • Input types: TrackingError, StopEvents read events; Lag and CodeShare the run's raw pairs (context); Repeatability a node's event logs of one command; PerformanceGain two event logs of the same held-out runs. Context (the part, its lever) is passed beside the data, as nuPlan's compute(history, scenario).

How it works

  • Streaming state: each node owns one Segmenter per signal; the open move or dwell carries across chunks; a stop attaches to the dwell event that holds its first row. One live update of the arm subtree costs 0.71 ms. A metric used alone has its own update / value / reset.
  • Computed once: composition is the dedup: the arm owns no segmentation (all 6 of its aliases read the servo's), the servo owns 2 (its output, and the raw plan / state for the lag). 12 aliases, 2 segmentations.
  • Gates: Check(alias, high, owner, level) per node; levels OK / WARN / ERROR / STALE (diagnostic_msgs); a parent's level is its worst child's, and the reason is named at the node that failed.
  • Across runs: node.groups(by) and node.values(entries), each alias by its own rule.

What happens to the existing code

  • robotdx.diagnostics.stock: its catalog becomes node declarations in robotparts; its formulas move to the event metrics here, so RobotDx would depend on robotparts for them (the cost of this home).
  • sim2real.metrics.actuator: deleted. CalibrationOutcome: a robot_msgs message.

Best when / loses when

Best when the deployment page should read as the robot reads (rack → arm → servo), with every red cell naming the part that failed and the event to open. Loses when a metric does not fit the move / dwell event model (a camera's single-instant multi-DOF error), when the scenario's roll-ups need hand-written tables over the ledgers, and because the formulas sit high in the stack (above robot_models), where RobotDx and sim2real must reach up for them.
